## Purpose

定义系统当前房客匹配业务的办结条件及结果语义，通过有权访问的客户需求和当前可用的在售房源提供可解释的候选，使经纪人能识别有效匹配、零候选及尚未完成的输入或依赖处理。

## ADDED Requirements

### Requirement: 按受权客户需求匹配当前在售房源

系统 MUST 确认人员档案具有 `CUSTOMER` 角色，并按该买方角色独立的 `owner_user_id` 或授权管理员范围验证需求资料的访问权限。人员主档原登记负责人不是买方需求授权的唯一依据。角色适用性 MUST 根据实际角色成员关系判断，兼容的单值 `profile_type` 不代表该人员的全部角色。结果仅包含当次有权使用、可用且在售的房源，并 MUST 包含每套房源的稳定引用、可展示资料、资料版本及有事实支持的匹配理由。金额与面积使用明确单位，缺失值表示未知。

#### Scenario: 档案只有业主角色
- **WHEN** 匹配请求引用只有 `OWNER` 角色、尚无 `CUSTOMER` 角色的人员档案
- **THEN** 系统提示需要买方角色及适用需求，不能仅因存在同名偏好字段而执行买方匹配

#### Scenario: 买方与业主双角色参与匹配
- **WHEN** 人员档案同时具有 `CUSTOMER` 和 `OWNER` 角色，调用人有权读取其买方需求
- **THEN** 系统使用该人员的买方需求进行匹配，同时保留其原有业主角色及房源关联

#### Scenario: 买方角色负责人不同于主档登记人
- **WHEN** A 原先登记了业主人员档案，B 后续按获准流程添加买方角色并成为其独立负责人
- **THEN** B 可以按该角色需求发起匹配，系统不能仅因主档登记人为 A 而拒绝 B，也不能仅凭主档登记人身份把该买方需求和匹配结果开放给 A

#### Scenario: 兼容字段只显示业主
- **WHEN** 人员档案的实际角色成员关系含 `CUSTOMER`，旧 `profile_type` 字段仍为 `OWNER`，且调用人有买方需求访问权限
- **THEN** 系统按实际角色及需求授权受理匹配，不能因兼容字段只有单一值而拒绝该人员

#### Scenario: 只有业主引用权限的经纪人发起匹配
- **WHEN** 人员档案具有买方角色，但调用人仅可在其房源中引用该人员的业主角色
- **THEN** 系统拒绝读取未获准的买方需求及其匹配结果，不能从业主引用推导买方资料授权

#### Scenario: 联系资料投影用于业主读取
- **WHEN** 系统为关联房源负责人返回共同业主的姓名和联系方式
- **THEN** 该投影不携带买方条件快照、需求摘要或匹配结果；需要匹配时仍通过买方角色授权入口独立读取

#### Scenario: 返回匹配候选
- **WHEN** 客户需求足以匹配，客户与房源数据均可用
- **THEN** 系统返回当前可用在售候选及逐套匹配理由，理由对应此次使用的客户需求和房源事实

#### Scenario: 候选在输出前失去可用资格
- **WHEN** 检索召回的房源在输出前已经下架、成交或失去访问权限
- **THEN** 结果排除该房源，不能继续用旧缓存作为可用在售候选

### Requirement: 预算上限和区域是匹配硬条件

开始匹配 MUST 具有明确的区域范围和预算上限。每套候选 MUST 满足当前区域范围且挂牌价不超过预算上限。评分和软偏好不得抵消硬条件。硬条件所需的房源事实未知或无法核实时，该房源不能计入已满足条件的候选。

#### Scenario: 户型面积合适但价格超出
- **WHEN** 用户预算上限为 300 万元，一套房源为 310 万元，其他条件均合适
- **THEN** 该房源不进入本次候选，匹配理由不能将其描述为预算符合

#### Scenario: 价格和户型合适但区域不符合
- **WHEN** 房源位于用户指定区域范围以外
- **THEN** 系统排除该房源，不能用其他偏好的高分补足区域条件

### Requirement: 明确指定的几房几厅严格满足

用户明确指定的房间、厅数量 MUST 作为精确约束。用户明确了其中一项时只约束已明确的项目，其余按已收集信息处理。其他可放宽的户型偏好及面积 SHALL 作为软条件使用。候选理由 MUST 如实说明软偏好的满足或偏离情况。

#### Scenario: 明确三房两厅
- **WHEN** 用户明确要求三房两厅
- **THEN** 两房两厅或三房一厅不能作为满足该次户型要求的候选

#### Scenario: 面积偏好可以放宽
- **WHEN** 区域、价格上限和明确的房厅条件均满足，但面积偏离偏好范围
- **THEN** 该房源可按软匹配规则参与排序，并显示实际面积与偏好差异

### Requirement: 完全满足偏好的候选优先展示

结果 MUST 将满足全部软偏好的候选排在放宽候选之前，随后展示仍满足全部硬条件的放宽候选，并标注偏好值、实际值及差异。仅在同一组内使用评分比较先后。

#### Scenario: 放宽候选分数较高
- **WHEN** 两套房源都满足硬条件，一套满足全部软偏好，另一套面积偏离且模型或规则分数更高
- **THEN** 满足全部软偏好的房源先展示，放宽候选随后并显示面积差异

### Requirement: 从对话提取需求及补充必要信息

Agent SHALL 利用客户档案和本次对话中有依据的信息提取区域、预算和户型要求，在运行态保存实际用于匹配的条件及来源关联。每次匹配 MUST 对应其实际采用的运行态条件，档案需求的最终提交遵循会话结束规则。缺失区域、预算上限或存在不能确定的含义时，MUST 经 Supervisor 提问并续接原任务。系统不得自行生成没有依据的预算或区域。

#### Scenario: 对话已有预算和区域
- **WHEN** 对话已经明确“天河区，总价不超过 300 万”，档案中尚未填完整
- **THEN** Agent 可提取这些条件用于本次匹配，并使结果关联到此次使用的条件及对话依据

#### Scenario: 对话缺少预算上限
- **WHEN** 客户档案和对话都没有明确预算上限
- **THEN** Supervisor 请求补充预算，匹配保持等待，暂不查询并完成一次房源推荐

### Requirement: 匹配输出即完成本次任务

系统 MUST 在成功取得来源结果并返回候选和理由后将该次匹配报告为完成。完成条件以可用的结构化输出为准。本期业务完成点为匹配结果交付。

#### Scenario: 候选结果成功返回
- **WHEN** Supervisor 获得并验证本次候选与理由
- **THEN** 本次匹配任务完成，页面展示其条件与结果。同一会话继续调整运行态需求并重新匹配时，形成新的匹配记录，档案需求按会话结束规则提交

#### Scenario: 成功检索但没有合适候选
- **WHEN** 所需数据均查询成功且符合本次约束的候选为零
- **THEN** 系统显示本次无匹配房源及允许说明的原因，按成功完成的匹配处理

### Requirement: 输入不足与来源失败保留明确处理状态

系统 MUST 区分输入不足、无权操作、来源不可用和正常零候选。受监督流程需要补充需求时 SHALL 通过 Supervisor 的统一等待与恢复契约处理，执行失败返回稳定错误。结果状态、任务状态和完成事件 MUST 一致。

#### Scenario: 需要补充需求
- **WHEN** 领域确认现有输入不足以执行本次匹配
- **THEN** Supervisor 展示待补充信息，任务等待用户，页面不把尚未匹配呈现为“没有房源”

#### Scenario: 房源源服务失败
- **WHEN** 房源查询或结果复核未能完成
- **THEN** 系统显示来源失败或待重试，保留调用关联，本次不发送成功完成事件

### Requirement: 匹配结果保留为可恢复的会话历史

系统 MUST 在原会话历史中保留每次匹配的客户引用、实际运行态条件、需求摘要、候选与理由或零候选原因、房源事实版本及观察时间。结果 SHALL 通过稳定的业务记录或不可变执行证据关联会话、运行和调用。Memory 交付沿用可信来源引用、内容摘要及可靠回执，恢复时复用已完成结果。历史展示 MUST 清楚表达该次结果采用的条件和事实时间。

#### Scenario: 回看同一会话的多次匹配
- **WHEN** 经纪人在一次对话中调整需求并完成多次匹配，之后回到该会话查看
- **THEN** 系统能分别恢复各次实际条件、候选、理由和事实版本，保留对话顺序及对应的客户关联

#### Scenario: 零候选结果可以回看
- **WHEN** 一次成功匹配返回零候选，经纪人之后回看该会话
- **THEN** 系统展示当次条件、无匹配房源的结论及其原因，使其与来源失败或尚未执行区分

#### Scenario: 归档交付回执丢失
- **WHEN** 已完成匹配的事实来源仍可恢复，但 Memory 交付需要重试
- **THEN** 系统以原来源、事件及内容摘要补交付，复用该次匹配结果，同一结果只形成一份有效历史记录

### Requirement: 恢复旧会话时呈现当前档案差异

重新进入旧会话继续沟通时，系统 MUST 按当前授权恢复原对话，并读取当前已落档的买方需求，将其与旧会话的需求条件和基线版本比较。存在差异时 MUST 显示相关字段的原值、当前值及版本或时间。回看与恢复本身保持历史事实的时间含义，新的匹配仍须核验当前房源状态和访问范围。恢复后的新表达继续保存在本次运行态，只有新的明确结束事件才能触发最终需求提交，提交同时校验最终意图与档案版本。

#### Scenario: 旧会话落后于当前档案
- **WHEN** 旧会话采用的预算为 300 万元，而当前档案已在另一沟通中形成 350 万元的新需求版本
- **THEN** 系统恢复旧对话并展示两次需求的差异，经纪人可在看到差异后继续沟通，历史恢复不会自动生成新的档案需求版本

#### Scenario: 旧候选已下架
- **WHEN** 历史匹配候选当时在售，回看时该房源已经下架
- **THEN** 系统按当前权限展示获准的历史记录并标明其历史条件和观察时间，再次匹配以当前房源事实判断可用候选

### Requirement: 匹配 Agent 复用必需的 Memory 生命周期

Supervisor 和参与匹配的官方领域 Agent MUST 在模型及业务工具执行前按可信 owner、domain、agent 与会话上下文读取并复核获准工作集，并在完整轮次后按许可归档。来源、身份和授权校验遵循既有 Memory 契约，关联标识只用于定位。客户需求版本及匹配记录由其业务真源维持，Agent 的个人偏好记忆继续适用既有私有范围。基础记忆不可用与合法空历史 MUST 具有不同的执行结果。

#### Scenario: 合法的空历史
- **WHEN** Memory 成功核验当前上下文，返回没有既往匹配记录的合法空工作集
- **THEN** Agent 可根据当前获准档案及本次对话继续处理，并按既有生命周期保留本轮证据

#### Scenario: 基础记忆无法核验
- **WHEN** Memory 身份、当前授权或基础工作集读取失败
- **THEN** 当前轮次在尚未执行的模型及业务工具之前停止，返回明确的依赖或授权结果，保留可恢复的已接受事实

#### Scenario: 历史来源权限撤销
- **WHEN** 已恢复的历史来源在后续模型、工具或展示边界失去当前许可
- **THEN** 系统重新核验并拒绝使用或输出失效来源，保留已完成调用的可信关联，恢复不以重新执行匹配来替代来源授权

### Requirement: 负责人转交仅移交该客户业务历史

管理员转交买方负责人后，系统 MUST 按新的买方角色权限向接收人提供该客户的需求变化时间链和匹配记录。接收人以自己的可信上下文从获准的客户业务来源读取这些记录，每份记录 SHALL 保留原实际操作人、会话来源及事实版本。接收人访问由该客户范围限定，原会话及个人 Memory 工作集的 owner 记录保持原身份，完整私有会话、其他客户内容和个人偏好继续按各自原有权限处理。

#### Scenario: 新负责人读取客户历史匹配
- **WHEN** 授权管理员将某客户的买方负责人由 A 转为 B，B 查询该客户的业务历史
- **THEN** B 可查看该客户的需求变化及匹配记录，仍能识别原操作人与来源，返回内容限定在该客户的获准业务记录

#### Scenario: 业务历史引用包含原会话标识
- **WHEN** B 从移交的匹配记录获得 A 原会话的来源引用
- **THEN** 该引用仅用于业务记录追溯，读取原完整会话及其他记忆仍分别校验其 owner、domain、agent、用途和当前授权
