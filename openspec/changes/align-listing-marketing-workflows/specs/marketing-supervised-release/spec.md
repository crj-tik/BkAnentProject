## Purpose

规范受 Supervisor 编排的房源营销审核与发布，使用户能确认具体草稿版本、授权一次明确的对外发布，并在渠道结果未知或人工确认发布失败时继续沿原记录处理。

## ADDED Requirements

### Requirement: 发起人审核本次草稿版本

系统 MUST 由 Supervisor 协调营销草稿生成与人工审核，并将审核动作绑定到当前已认证的发起人和所展示的草稿版本。发起人 MUST 能自行审核其发起的草稿。审核通过和执行渠道发布 MUST 各自具备独立的人为确认。

#### Scenario: 发起人提交审核决定

- **WHEN** 当前已认证的发起人在 Supervisor 交互中获得待审草稿
- **THEN** 系统展示版本及对应内容，允许该发起人提交该版本的审核决定，且在收到独立的发布确认前保持渠道未调用

#### Scenario: 审核要求修改或驳回

- **WHEN** 发起人要求修改或驳回当前草稿
- **THEN** 系统保留该版本及其审核决定，并返回草稿阶段。修改形成新版本，新版本需要新的审核决定

### Requirement: 草稿审核前复核房源状态和价格

系统 MUST 在草稿确认通过前读取房源域的当前在售状态和价格，并将用户决定绑定到所见草稿版本与本次复核结果。发现价格变化时，系统 MUST 展示原价格和当前价格，允许发起人选择更新草稿，或明确保留草稿价格并记录该决定。房源已下架或失去在售资格时，系统 MUST 返回草稿并提示原因。房源当前状态无法确认时，系统 MUST 保持审核未通过并提示复核未完成。

#### Scenario: 审核过程中房源下架

- **WHEN** 用户准备确认草稿，房源复核结果显示已下架
- **THEN** 系统将任务退回草稿，说明所选房源当前不可选并提示重新选择，保持草稿版本未获批准

#### Scenario: 用户决定保留草稿价格

- **WHEN** 草稿展示的价格与当前价格不同且房源仍在售，发起人明确选择按草稿价格通过
- **THEN** 系统记录操作人、操作时间、草稿版本、原价格和复核价格，按展示的草稿版本记入审核结果

#### Scenario: 用户决定更新价格

- **WHEN** 发起人对价格变更提示选择更新草稿
- **THEN** 系统按新价格形成草稿新版本并展示待审内容，原版本的确认无法批准该新版本

### Requirement: 发布使用确切的已审核材料

草稿通过审核时，系统 MUST 固定已审核的正文、素材及本次审核采用的房源事实。发布计划 MUST 绑定该草稿版本以及本次发布的渠道和目标账号。已审材料进入发布后，系统 MUST 使用固定内容及房源事实执行这份计划。变更正文或素材必须重新审核其新版本，变更计划绑定时必须重新展示并确认对应计划。

#### Scenario: 草稿通过后房源数据变化

- **WHEN** 用户审核通过所展示的草稿版本，发布前房源当前状态或价格再次变化
- **THEN** 该发布计划继续引用原已审版本及其固定事实，发布阶段对计划本身执行确认与权限检查

#### Scenario: 发布前正文、素材或目标账号变化

- **WHEN** 待发布正文、素材或目标账号与用户此前所见的版本或计划不同
- **THEN** 系统保留原审核和计划确认记录，按变更范围重新展示应审核的草稿版本或待确认的发布计划，等待相应的人为决定

### Requirement: 渠道发布必须经过用户确认

Supervisor MUST 向具备发布权限的用户展示本次计划，再接收其对当前版本和目标账号的明确发布操作。渠道执行发布 MUST 等待该操作生效。需要通过 MCP 登录部门共享渠道账号时，系统 MUST 展示扫码登录入口。扫码状态变化只推进登录准备，登录成功后 MUST 等待本次确认人在原确认页再次点击发布。

#### Scenario: 用户已审草稿但尚未点击发布

- **WHEN** 当前草稿已通过审核且系统已展示发布计划，用户尚未确认执行该计划
- **THEN** 系统保持计划待发布确认，并保持渠道未调用

#### Scenario: 共享账号需要扫码

- **WHEN** 用户点击发布，系统发现本部门共享渠道账号需要扫码登录
- **THEN** 系统展示当前部门的扫码入口，登录成功后提示再次点击发布，保持渠道未调用直至收到这次确认

### Requirement: 发布状态反映真实渠道结果

系统 MUST 按发布尝试保存渠道调用结果并向用户区分成功、失败和未知。MCP 明确返回成功时 MUST 记录对应尝试的渠道结果并办结。结果未知 MUST 保留在原尝试上，等待核对。原确认人或对计划所属部门具有发布管理权限的管理员 MUST 能登记核实未发布，并保留人工操作人、时间、依据及原调用结果。

#### Scenario: 渠道明确返回成功

- **WHEN** 系统收到能够确认当前尝试发布成功的渠道结果
- **THEN** 系统在该尝试下记录成功及渠道凭据，并向用户显示成功

#### Scenario: 渠道调用超时或回执丢失

- **WHEN** 系统无法确认当前尝试是否完成外部发布
- **THEN** 系统保留原尝试并显示结果未知，向用户提供核对该尝试的入口，等待明确结论

#### Scenario: 有权人员核实渠道发布失败

- **WHEN** 具备相应权限的用户核实了原尝试未完成发布并提交失败确认
- **THEN** 系统更新原尝试的可见结论，保留原调用结果，并记录人工确认的操作人、时间和依据

### Requirement: 重发是独立的受权发布尝试

系统 MUST 在存在原尝试的人工核实未发布记录，且原确认人或计划所属部门的发布管理员再次确认时受理重发。重发 MUST 建立关联原尝试的新记录，并通过当前发布权限、确切计划及渠道账号准备的检查。针对同一次重发确认的重复提交 MUST 归并为同一次尝试。

#### Scenario: 有权用户重发明确失败的任务

- **WHEN** 原尝试已经人工核实未发布，有权用户再次核对计划并确认重发，且渠道账号已就绪
- **THEN** 系统建立新的发布尝试并关联原尝试，分别保留各自的状态与结果

#### Scenario: 尝试未知或操作者无重发权限

- **WHEN** 原尝试结果仍未知，或当前用户对该任务没有重发权限
- **THEN** 系统保持原尝试，展示相应的待核对或权限不足结果，并保持渠道未被再次调用
