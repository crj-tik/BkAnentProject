## Context

现行 `ListingManagementServiceImpl.changeStatus` 的状态表允许 `PENDING_REVIEW → ON_SALE`。挂牌价已经有历史记录。KI-290 已在房源候选、检索与新建营销草稿入口加入在售条件。

`CampaignLifecycleService.prepare` 与 `confirm` 在发布段依赖当前房源快照。仓库有营销内容、内容 revision、发布计划、请求、尝试、回执和事件表，当前投放提供者为模拟实现。旧营销内容的审核状态还不能证明具体素材版本已被审过（KI-276）。

当前 Supervisor 审批暂停发生在自己即将执行的工具调用之前。`OfficialA2aAgentClient` 将 A2A 输入或鉴权等待映射为普通等待，现有结构不足以把领域的业务审批、安全恢复和异步完成事件接起来。当前审批恢复以原任务所有者为边界，部门管理员代办需要授权到具体动作和资源。现状与目标表字段见[数据流与字段](dataflow.md)。

## Goals / Non-Goals

**Goals**

- 从经纪人登记到管理员审核、首次上架、经纪人调价及下游引用，能按业务记录回溯责任人与版本。
- 营销在一个任务内完成草稿自审和发布确认，能追溯房源快照、人看到的版本、部门账号及每次实际尝试。
- 为后续领域提供统一 A2A 信封、暂停/恢复、授权和错误语义。领域为每个动作提供独立输入/输出 Schema 与验收条件。

**当前待定**

- 影响房源真实性的其他字段在上架后如何更改，谁可下架，何时需重新审核上架。先沿用现行规则，按后续业务决定另行修改。
- 其他业务域的办结条件、人工角色、数据输入与输出，沿用本契约逐域确认。

## Decisions

### 1. 房源首次上架与日常维护

经纪人带团队范围和可信身份代业主从 Customer 域选择 `OWNER` 档案。端到端保留 `owner_customer_id`（业主档案）与 `owner_user_id`（跟踪责任人）的区别，旧 `broker_id` 只走已验证的兼容映射。管理员从待办查看登记信息、业主关联和现有可用资料，对提交版本作真实性审核。基础字段采用目前的标题、地址、户型、面积、挂牌价，加有效业主档案的校验。已有证件、合同、委托、OCR 和核验字段继续储存并按原权限展示。

保留生命周期状态 `PENDING_REVIEW` 表示待上架，另以审核记录区分未提交、待审核、退回、已通过。建议新增房源首次上架审核记录，保存送审版本、送审/审核人员、时间、结果与退回意见。审核通过后执行明确的 `LIST` 状态转换。两步可在 Listing 同一事务里写入审核结果、状态历史与索引待发送事件。校验提交版本并原子更新，避免审核时资料已换。首次上架从任何入口执行都要求有效通过记录。已有在售房源不凭空生成初审结果。

负责经纪人按既有房源写权限直接维护挂牌价，显式单位元，写入价格历史并维护旧万元投影。审批流程与在售日常调价独立。状态与价格都通过 Listing 读取和复查，其他服务只持有业务用途所需快照。对比、匹配、搜索与营销候选采用在售门槛，管理读保留非在售的负责人/管理员可见范围。

### 2. Supervisor 与领域之间统一排队、暂停和恢复

沿用官方 A2A Message、Task、Artifact，结构化业务数据置于 A2A DataPart。工作流由 Supervisor 创建，保存运行、子 Task、`messageId`、因果消息和审批关联。调用方在分派前校验请求，接收端验证签名身份、动作权限、当前资源和请求 Schema，Supervisor 再按声明结果 Schema 校验响应。`schemaVersion` 版本是共用信封，`contractVersion` 由动作注册表固定。动作入口、输入、输出和必要权限从同一登记读取，校验失败停在该边界并给出可关联诊断。字段及动作见[一期 A2A 契约](contracts/README.md)。

交互型 Agent 委托用 `SUCCEEDED` 返回结构化产物，用 `WAITING_HUMAN` 返回不可变的目标引用、版本、待办和可选决策，用 `FAILED` 返回稳定错误码和恢复方式。另有 `WAITING_DOMAIN` 表达领域依赖。等待状态落到 Supervisor checkpoint，和已办结事件互斥。页面只提交记录 ID、有限选择和该动作所需反馈。Supervisor 重新鉴权，按审批 ID、业务版本和决策请求 ID 去重，就同一领域子任务续接。领域再校验审批凭据对应的目标版本并落业务结果。A2A 的运输身份与批准人的签名授权上下文分开验证。任务创建人、审批人、部门账号分别留痕。

领域若需要另一个业务域，返回结构化依赖 `WAITING_DOMAIN`，带目标领域、动作和受约束数据。Supervisor 评估当前技能与动作权限后发起 A2A 委托，用子任务结果恢复原领域，保留两段关联。依赖声明本身不授予调用权，业务域拒绝、网络/协议失败和成功结果分别入记录。模型仍可理解目标、生成内容和提出下一步，版本、角色、状态门槛和副作用由服务端校验。

### 3. 营销草稿审核以已存档版本为目标

1. Supervisor 委托营销 Agent。营销经 Supervisor 请求 Listing 的当前房源事实。得到可用快照后，生成并保存草稿及精确的素材版本，提交草稿审核。重新生成和继续原任务引用同一个业务任务及不同 revision。
2. 发起人通过 Supervisor 打开草稿审批，退回时录入意见。选择通过时，在写审核结果前经 Supervisor 复查房源引用，保存本次读取的状态与版本。不可用时保留任务和已有草稿，提示经纪人更换房源并回到草稿环节。来源不可达时保留待校验进度和可重试提示。
3. 房源在售且价格变动时展示快照价、当前价。选择更新时按新事实生成新 revision 并重新审核。选择沿用时记录旧价、新价、事实版本、通知及本人选择，日志描述“已提醒调价，用户选择沿用旧价格”。决策提交与该提醒的版本绑定。若用户等待期间再出现调价或下架，优先按最新的变化重新呈现。最终通过绑定选定文本、素材、房源快照与决策记录。
4. 发布准备消费已通过 revision，生成精确的计划和目标渠道，页面呈现要发布的标题、正文、素材以及部门账号。此后仅使用草稿确认时冻结的内容与事实。在发布确认及执行中复核计划版本、授权和登录会话，发布过程不查询房源状态和价格。变更正文或素材需要回到草稿形成新 revision，再按审批规则处理。

### 4. 初次发布、扫码恢复与人工重发

营销 Agent 暴露 A2A 业务入口，在内部调用已登记的发布 MCP 工具，适配层才连接 `xpzouying/xiaohongshu-mcp`。部门账号会话是渠道资源，真实操作人来自系统登录和授权。二维码采用短期受控引用，日志只存流程状态及引用标识。若发布前发现会话失效，切换到 Supervisor 的登录处理节点。公共账号扫码恢复只改变渠道登录状态并重新呈现原计划，原确认人再次点击，才提交本次执行授权。

每次点击生成稳定请求身份，计划与尝试是一对多。提交前持久化等待调用的尝试，执行前认领，同一点击只能认领一次。MCP 返回明确成功后记录回执并办结。发送后断开、超时、回执缺失等无法确认外部结果的情况保留“结果待核对”，支持人工核对。外部 MCP 未提供可依赖的幂等能力时，不自动重发可能已到达的请求。

原确认人或持有本部门发布管理权限的账号可登记人工核对与“未发布”，保留原成功回执及其证据来源。经过再次确认后，同一个计划新增尝试并关联前次记录，使用本次实际操作者的授权。扫码恢复后由本次重发确认人再次点击。重复回调、刷新和重连都只返回现有尝试。收到明确成功的尝试按业务规则办结，外部是否实际可见仍可人工纠正。

### 5. 兼容与实施顺序

优先完成信封、动作登记、认证和 Supervisor 等待/恢复能力，再接入房源审核与快照读取，随后接入营销内容确认、发布和重发。复用现有的 Campaign 记录和渠道提供者边界。对活跃的旧营销生命周期提案，以本提案补充受监督链路的职责与入口规范，切换时核对 A2A 技能声明、旧发布入口及兼容调用是否遵守同一确认规则。

迁移新增字段先允许旧数据存在，已在售和历史营销记录按真实状态保留。缺少可证明的审核版本时，开启新的发布动作必须取得符合新契约的草稿审核及发布确认。从历史只读记录恢复时识别原版本和升级边界。数据库改动走受管初始化清单及迁移校验。

## Risks / Trade-offs

- 营销审核时的房源复查是跨域读取，保存 Listing 当次观察到的版本和时间。发布阶段继续使用已经确认的资料。
- 管理员委派办理范围按部门、权限、动作和目标计划同时验证。审批创建、接收和执行都要检查当前范围，权限撤销后不能续接。
- 信封的结构校验只覆盖类型、必填字段和判别分支。人员权限、价格关系、动作与数据 Schema 的登记匹配、同一次按键的去重和合法状态转换由应用校验，有独立验收用例。
- 认证上下文、过期二维码、资料证件文件、外部渠道会话的原始数据只保存在受保护的边界内。A2A 产物、SSE 和审计只包含当次业务需要的最小字段。
