## Context

Auth 的 `user_account` 保存 displayName、旧 roleCode 和 tenantCode；版本化授权提供多角色、快照、outbox 和请求级签名。`businessAdmin` 当前直接获得全部有效权限，一些管理入口还检查此标记。Auth 存储 user→BROKER 与 user→STORE，客户和房源仍以 brokerId 校验归属。KI-204/206 的员工、收款和提醒关联仍有缺口；STORE 已新增映射，旧问题描述需按事实更新。`unify-versioned-permission-context` 尚有未完成任务，变更之间需协调协议和验收，不得相互宣称完成。

## Goals / Non-Goals

**Goals:** 统一用户档案、组织成员、显式岗位/管理角色和角色权限；将业务中确实表示平台用户的负责人安全迁移到 userId；为一公司、门店、运营部门及两位用户完成实际开发环境 API 验收。

**Non-Goals:** 不实现 HR 工资档案、客户外部账号、自动推导隐性角色、支付主体或真实支付；不按姓名、工号、数字相等推断历史关系，不关闭现有未证明安全的业务门禁。

## Decisions

### 1. Auth 暂为组织权威

采用 `auth_org_unit`（id、公司/门店/部门类型、parent_id、状态、版本）和 `auth_org_membership`（user_id、org_id、状态、有效时间、主归属标记、审计字段），在事务中防循环、跨公司非法关联和并发产生多个当前主归属。主归属第一阶段至多一个；可保留带有效期的其他成员关系，但不能推导权限。门店业务 storeId 与组织节点显式一对一绑定并校验真源；若门店真源尚不存在，先将组织门店作为受控真源并定义与现有 STORE 的一对一回填规则，不将不相干数字直接等同。

组织管理与成员变更使用明确的管理权限与审计；本人查档/修改 displayName 为基础操作。现有 `/auth/me` 保留字段并增补组织摘要，PATCH 本人档案不得接收角色、组织、状态或 actor。只读公用信息和敏感成员列表分别限定访问范围。内部服务使用受信调用和签名结果获取适用组织范围；门店成员变更与授权版本、outbox 同事务推进，已有上下文受既有最多 30 秒 freshness 和硬截止限制，不能为每个 Graph 节点访问 Auth。

### 2. 所有权限经角色

岗位与管理是角色类型，分配方式第一版为显式授予。有效权限是有效用户角色、有效角色权限和有效目录的交集/并集；不提供 wildcard 或管理员直接全权限。先导出每个旧管理员的有效权限，创建不可通过一般用户授予入口分配的待迁移管理员角色并显式绑定当前权限，先以影子计算与旧权限对账，暂不把该角色绑定给真实用户：旧标记仍能独立撤销，若先绑定，撤销标记后角色仍会保留全部权限。完成受保护的管理员授予/撤销同步和最后管理员保护后，才在授权写锁内以事务化方案绑定用户并切换计算和管理入口，重新对账并推进版本、outbox。`businessAdmin` 暂作从角色投影的兼容字段；搜索所有服务对标记的特判，逐项迁移，不能只修改 Auth 计算器。旧运行不得突破原 scope 或硬截止。

### 3. userId 归属与旧 brokerId 并行迁移

逐域盘点 brokerId 的语义、数据量及所有 REST、RPC、MCP、RAG、A2A、消息消费者。对真实平台用户 owner 增加 owner_user_id 和索引，生成可复核的一对一映射账本，只有确证唯一映射可回填；缺失、冲突、删除用户和历史关联变更分开处理。上线兼容读写前定义唯一写入权威、写入事务及并发回填版本检查，避免双写不一致；迁移期间旧字段仅用受信映射处理，不从用户输入或模型补全。域切换按版本/开关完成，任何域可独立回退到兼容读取，禁止删除未迁移数据。跨域涉及员工、收款或历史合同的字段先验证语义，不能假设它们都是平台账号。

### 4. 样例、接口与运行环境

提供受保护的管理 API 用于组织/成员、角色和用户的创建、读取、变更及审计；具体参数与既有 ApiResponse 和鉴权约定一致。开发环境显式运行可重复的初始化工具，按稳定外部标识寻找样例，存在冲突时停止而非覆盖；公司、门店、运营部门及 broker/operations 两个非管理员用户分别有独立身份、角色和成员关系。密码运行时生成或由忽略的 .env 提供；日志不输出凭据或 token。样例角色只授予已确认的受限操作，基础功能不配权限码；不足的受限业务明确拒绝。

所有数据库结构/必要基线数据通过 checksummed manifest 及 fresh/upgrade/repeat 检查；开发样例用户不写入通用生产种子。Nacos/Compose 只新增有实际消费者的配置并列出默认值、环境映射及密钥引用；核对运行容器实际值。部署通过 `wsl.exe -d Ubuntu` 在 `/mnt/d/project/BkAnentProject` 使用 Docker，不清理卷。环境使用正反 API 测试，无前端的路径用 API；浏览器专项仍单独冻结。

## Risks / Trade-offs

- [旧 businessAdmin 消费者暗中扩权，或撤销旧标记后预先绑定的管理员角色仍保留权限] → 全仓清点并逐项改造；仅准备未授予用户的管理员角色，待授予/撤销和最后管理员保护就绪后成组切换，对账两种撤销路径。
- [组织关系过期但签名仍可用] → 同事务更新版本并受 freshness/失效通知和硬截止约束；下游门店关系按已验证 scope 和域资源检查。
- [历史归属映射缺失或一对多] → 隔离并人工核实，不猜测；不为完成迁移改变财务/合同事实。
- [并行会话修改共享清单或部署] → 读取并保留既有变更，迁移序号/manifest 和运行环境实施前复核，不提交其他会话文件。

## Migration Plan

先完成权限和 ID 消费清单及管理员权限等价报告；添加可重复 schema 并部署兼容读取；准备无用户绑定的管理角色并影子对账，待授予/撤销联动及最后管理员保护完成后再绑定并切换管理员判定；组织成员与 STORE 建立可信映射；各域按唯一写入和受控回填逐步切换 userId；最后验证无消费者后退役旧身份字段。数据库只 forward 迁移；回退切换兼容版本/开关并保留新旧数据，只有在权限等价与协议兼容已验证时回滚服务，禁止回到已知扩权或匿名旁路。样例账号在开发栈显式初始化并 API 验收；保留审计与映射账本。
