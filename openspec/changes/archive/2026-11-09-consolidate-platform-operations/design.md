## Context

现有 `business-service`、`business-review-service`、`knowledge-service` 各有独立接口、数据库、授权和 Agent 身份。复盘调用知识的 HTTP 接口；知识通过受限视图读取访谈脱敏来源。合同和结算在 Gateway、Agent、Memory、RAG 和初始化中均有注册。相关 change 仍有未完成任务。

## Goals / Non-Goals

**Goals:** 使用一个可部署服务和一个领域库承接三个功能，退役合同与结算，交付完整配置、数据库和前端功能清单。

**Non-Goals:** 不将访谈采集、房源、客户或营销并入平台经营域；不把模拟数据当作真实业绩。

## Decisions

1. 服务命名 `platform-operations-service`，域名 `platform-operations`，数据库 `bk_platform_operations`，接口前缀 `/platform-operations/**`。内部保留 analytics、review、knowledge 的代码和事实边界。相比仅在网关合并，单服务能消除域内 HTTP 跳转与重复部署。
2. 逐接口盘点旧功能并建立新旧映射；迁移所有仓库调用方后移除旧入口。域内知识读取改为本地调用，同时保留来源撤回、版本核对和失败关闭语义。跨域房源与访谈读取仍受授权及来源校验约束。
3. 合并数据库时保留领域表的状态、版本和主键语义；重新建立访谈受限视图与最小权限账号。用户确认无正式历史资产，开发数据可按受管迁移重建；先盘点现有开发数据和初始化基线，保留必要基础记录，不伪造业务数据。已有迁移文件与校验摘要不可改，追加迁移并验证新库初始化及已有库升级。
4. 用户确认使用一个平台经营 Agent；按经营分析、复盘和知识运营分别隔离工具调用与操作权限，并保留知识逐字稿输入防护及 Memory 正文隔离。服务身份与 Agent 注册切换前盘点现有身份、权限、Memory 与 RAG 使用者。STORE 范围来自可信 Auth 身份；审核人与 owner 分离、来源撤回和 Memory 私域保护不得因合并放宽。身份切换采用清晰的注册与撤销顺序，不把授权目录登记当作角色授权。
5. 合同与结算退役覆盖模块、RPC、网关、Agent/MCP、Studio、Auth、Memory/RAG 空间、部署模板、脚本、数据库及维护测试。历史迁移和设计记录保留；当前接口和配置不再暴露旧能力。
6. 用户确认每个用户最多关联一个门店，同一门店可以关联多个用户。Auth 使用独立的用户—门店关系表管理可信映射，保留原 BROKER 身份的唯一性；仅通过受授权管理入口变更，变更纳入 writer lock、授权版本和 outbox。签名上下文携带一个 STORE 身份，缺失、撤销或门店不匹配时失败关闭；不从请求参数或姓名推断门店。
7. 统一 Agent 对外只发布一张 Agent Card 和一个 A2A 入口。请求 metadata 的 `platformCapability` 必须精确为 `analytics`、`review` 或 `knowledge`；路由器先校验对应 `agent.workflow.invoke.platform-operations.<分支>` 签名操作，再选择独立工具集合和 Memory 上下文，不能由模型自行越权切换。知识分支必须先执行逐字稿输入防护再进入 Memory。取消任务、审批和身份撤销沿用已有语义；实现须覆盖分支间工具和记忆不可串用。现有固定身份 Memory hook 与单 owner Skill Card 发布器需要适配，不能直接把三个旧 Agent 的 Bean 一起装载。

## Risks / Trade-offs

- [合并扩大授权或泄露逐字稿] → 保持现有精确操作、门店范围、受限来源及 Memory 正文隔离，覆盖拒绝路径。
- [旧调用方或配置残留] → 按代码、网关、服务身份、数据库和模板分层盘点，并验证最终构建和运行链路。
- [已有 change 状态与新设计冲突] → 逐项映射未完成任务，记录替代关系，避免错误标记完成。

## Migration Plan

冻结接口和数据映射；实现新服务及迁移；同步调用方和配置；执行开发库迁移与初始化核验；退役旧模块和两项业务；执行后端、配置、数据库和调用链验收，更新前端清单。失败时停止切换并依据迁移前备份恢复开发环境；不重写已应用迁移账本。
